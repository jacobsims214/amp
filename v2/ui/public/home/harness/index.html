What it is

AMP's own harness, flown from your terminal

AMP stays harness-agnostic: Claude Code, opencode and any MCP client keep docking at the same board. AMP Harness is the built-in default. It already knows AMP's agents, skills, approvals and run records, so there is nothing to wire up.

One binary, written in Rust. Every setting has a command, so nobody has to edit a config file by hand.

You talk to

The manager. It turns a goal into epics, stories and tickets on the AMP board, then waits for you to approve the plan in the web UI.

It runs

Specialist workers on each approved ticket: backend, frontend, docs, designer, reviewers, researchers, media and the KB curator, each on the model you chose for its role.

It reports

Every worker's model, tokens, cost, branch and commit go on its ticket, so AMP's spend and trace views work with no extra step.

Beside the UI

The web UI stays where people approve plans, answer questions and review artifacts. The chat links straight to each ticket and to the Flight plan page.

Prefer another?

Keep it. The Claude Code and opencode plugins bring the same agents and skills.

Out of the box

Everything a crew needs, in one binary

What's in the harness today, before you configure anything. Each card ends with the command or the words you'd see.

01

A chat in AMP's colors

A full-screen terminal chat with AMP's dark and light themes. The header shows your server, you, the project and the ticket in flight; the status line shows questions, workers, plan approval and board counts, live.

/ticket · /questions · /plan · /workers · /open
02

Manager plus specialists

The manager dispatches specialist workers through AMP. Each worker that edits files gets its own git worktree and branch, so parallel tickets never touch each other's checkout.

ticket 2108 → .worktrees/2108 on amp-2108
03

Every run on the record

The harness fills in each worker's model, tokens, cost, branch and commit on its ticket. A worker that stops without closing its ticket is recorded as abandoned, with the reason.

#2108 · worker-backend · 42,180 in · 18,044 out · pushed
04

Your go, not the agent's

Only a person approves a plan, in the web UI. The harness never lets an agent approve it; when the manager hits a step that's yours, it stops and links you to the Flight plan page.

⏸ Waiting for your approval · /open plan
05

Any provider, a model per role

OpenRouter, an Anthropic API key, OpenAI, or your own OpenAI-compatible endpoint (vLLM, Ollama, LM Studio, LiteLLM, a gateway). The manager, workers and reviewers can each run a different model and thinking level.

amp-harness models set reviewer anthropic/claude-opus-5-5
06

Enterprise endpoints

Your company's endpoint, however it signs in: API key as bearer or header, Azure OpenAI, Microsoft Entra ID, OAuth client credentials, or a token command (an SSO helper, Vault, az, gcloud). Custom CA, mTLS and proxies too.

auth = "azure-entra" · ca_file · client_cert · proxy
07

Any MCP server

Every transport: stdio, Streamable HTTP and legacy HTTP+SSE, with OAuth login. Choose which roles may use each server. Servers defined in a repo start only once you trust them.

amp-harness mcp add github https://… --roles 'worker-*'
08

Bring your servers along

Import the MCP servers you already set up, once, when you ask. Secret-looking values move to the keychain on the way in.

Claude CodeopencodeVS CodeCursorClaude Desktop
amp-harness mcp import --from claude --dry-run
09

Your own agents and skills

AMP's 11 agents and 23 skills ship inside the binary. Override any of them, or add new ones, for yourself or for everyone who clones a repo.

amp-harness agents new sql-expert --from worker
10

Live reload

Change agents, skills, models or MCP servers from another terminal and the running chat picks it up: by itself a moment after the files settle, or at once with /reload.

agents: +sql-expert · mcp: +github ~fs
11

Keys in your OS keychain

Provider keys and logins are typed into a hidden prompt, checked with the provider and kept in the OS keychain. Never in a file, never as a command-line argument. CI uses environment variables.

amp-harness connect · /connect in the chat
12

Doctor

One command checks the server, your login, the project, every role's model and key, MCP servers, agents and skills, and says how to fix whatever fails.

amp-harness doctor · ok · warn · fail, with the fix
Install

One line. Then it asks what it needs.

The installer downloads the newest release for your platform, checks its SHA-256 and puts amp-harness in ~/.local/bin, with no sudo. In a terminal it then offers to run setup.

For yourself the default roster

Install · personal
curl -fsSL https://raw.githubusercontent.com/jacobsims214/amp/main/v2/harness/install.sh | sh

Setup signs you in to AMP, links the folder to a project and connects a model provider.

With your company's preset --preset

Install · org preset
curl -fsSL https://raw.githubusercontent.com/jacobsims214/amp/main/v2/harness/install.sh | sh -s -- --preset https://intranet.example.com/amp-preset.toml

Your admin's preset sets the AMP server, the model endpoint and each role's model. It holds no secrets: you're asked only for your own key and login. See enterprise rollout.

Upgrade

Run the same line again. It replaces the binary in place, never over a running one, and keeps your config, keys and logins.

Uninstall

Uninstall
curl -fsSL https://raw.githubusercontent.com/jacobsims214/amp/main/v2/harness/install.sh | sh -s -- --uninstall

Removes only the binary, and lists what it kept (config, keychain items, each project's .amp.json).

Build from source

The one-liner downloads the newest published harness-v* release, 0.2.0 today. To build from a checkout instead, you need git and rustup.

Platforms: macOS 13 or newer (Apple silicon or Intel), and Linux on x86_64 or aarch64 with glibc 2.35 or newer. Alpine and other musl systems aren't supported yet.

Build from source
git clone https://github.com/jacobsims214/amp.git && cd amp
# release build, installed by install.sh
make -C v2/harness install
First run

Three steps to your first mission

Setup asks only for what isn't done yet, and it's safe to run again. Running plain amp-harness in a new terminal does the same first run before the chat opens.

01

Sign in to AMP

Give setup your AMP server (amp.example.com or a full URL). It checks the server, then opens AMP's sign-in page in your browser. The login is kept in your OS keychain.

$ amp-harness setup
02

Link and connect

  • Link this folder to an AMP project, existing or new. Setup writes .amp.json at the repo root.
  • Pick a model provider: OpenRouter, Anthropic, OpenAI or your own endpoint. The key is typed hidden and checked.
03

Talk to the manager

Run it in your project folder and say what you want built. Approve the plan in the web UI when it asks. If anything looks off, ask the doctor.

$ amp-harness $ amp-harness doctor
Enterprise rollout

Your models, your endpoint, one preset

Say your company serves two models, engineer and orchestrator, from an OpenAI-compatible endpoint at api.example.com. An admin writes one preset file; everyone installs with one line and is asked only for their own key. Nothing contacts OpenRouter.

  1. Write the preset

    The AMP server, the endpoint, its models and which model each role runs on. A preset that holds anything secret-looking, an unknown key or a non-https URL is refused.

  2. Try it yourself

    amp-harness setup --preset ./enterprise-preset.toml, then amp-harness doctor.

  3. Host it on https

    For example https://intranet.example.com/amp-preset.toml. Setup fetches it only over https.

  4. Send the install line

    The --preset one-liner. Each person signs in to AMP, links a project and types their own key. CI uses --yes with keys from the environment.

enterprise-preset.tomlno secrets
[preset]
name = "Example Corp"

[server]
url = "https://amp.example.com"

[providers.example]
name = "Example AI"
base_url = "https://api.example.com/v1"
models = ["engineer", "orchestrator"]

[roles]
default = "example/engineer"
manager = "example/orchestrator"
reviewers = "example/orchestrator"
